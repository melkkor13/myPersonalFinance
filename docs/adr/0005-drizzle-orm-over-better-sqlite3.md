# 0005. Drizzle ORM over better-sqlite3

Date: 2026-09-20

## Status

Accepted

## Context

The application stores data in SQLite, which suits a single-user, self-hosted deployment. However, cloud hosting is a stated future goal, and a move to Postgres is plausible. The scaffold's Problem Statement therefore requires that SQLite-specific behaviour be confined to as few modules as possible, so that such a move is a contained change rather than a rewrite of every query.

Separately, hand-maintained row-to-type mappings drift from the schema silently, which is the same class of bug that the shared contracts package exists to eliminate at the HTTP boundary. The data-access layer deserves the same treatment.

Migrations must be reproducible, reviewable in version control, and idempotent.

## Approaches Considered

### Option A: Drizzle ORM over `better-sqlite3`

**Pros:**
- Query API stays close to SQL, so existing SQL knowledge transfers and the generated queries are predictable.
- Very thin runtime with no separate engine process or binary.
- Types are inferred directly from the schema definition, so a column rename surfaces as a compile error.
- `drizzle-kit` generates plain SQL migrations that are committed and reviewable.
- Dialect is swappable: a Postgres move changes the connection and dialect modules while repository query code largely stands.

**Cons:**
- Younger and less battle-tested than Prisma.
- The relational-query API is still evolving, so some patterns shift between versions.

### Option B: Prisma

**Pros:**
- Mature, with excellent developer experience, strong migration tooling, and Prisma Studio for inspection.
- Large community and abundant documentation.

**Cons:**
- Requires a separate schema language and a generated client, adding a codegen step and a second source of truth about the schema.
- Heavier runtime, with an engine binary to manage in packaging and deployment.
- Further from SQL, making query behaviour harder to predict and tune.

### Option C: Raw `better-sqlite3`, or Node's built-in `node:sqlite`

**Pros:**
- No abstraction at all; complete control over every statement.
- Minimal or zero dependencies; `node:sqlite` ships with Node 22.

**Cons:**
- Migrations must be hand-rolled, including tracking which have been applied.
- Row-to-type mapping is manual and unverified, so it drifts from the schema without warning.
- The hardest option to port to Postgres, since raw SQL and SQLite idioms would be spread throughout the repositories.

### Option D: Knex with hand-written types

**Pros:**
- Flexible query builder with long-established, well-understood migration tooling.
- Multi-dialect from the outset.

**Cons:**
- Result types are declared by hand and unenforced, so they silently diverge from reality.
- More boilerplate than Drizzle for the same queries.

## Decision

Adopt **Option A**: Drizzle ORM over `better-sqlite3`, with a deliberately narrow engine boundary.

- `src/db/sqlite.ts` is the engine module: it opens the `better-sqlite3` connection, applies `PRAGMA foreign_keys=ON` and `PRAGMA busy_timeout=5000`, applies `PRAGMA journal_mode=WAL` only for file-backed databases, and exports `ping()` for the health check.
- `src/db/client.ts` imports the Drizzle SQLite dialect and wraps that connection.
- Those two files, plus `src/db/migrations/**`, `drizzle.config.ts`, and `package.json`, are the only five locations where SQLite-specific identifiers may appear. A test asserts this. A Postgres move rewrites the first two, translates the committed migrations, and swaps the dependency; it is the repositories that stay portable, not the whole `db/` directory.
- `drizzle-orm` may be imported only in `*.repository.ts` files and under `src/db/**` — never in routes, services, or plugins. Separately, no `*.service.ts` may import from `src/db/**` at all, so services reach data only through their module's repository. Both rules are asserted by tests.
- Raw SQL is disallowed outside `src/db/sqlite.ts` and `src/db/migrations/**`. The health check's `SELECT 1` therefore lives in `ping()`, with `health.repository.ts` wrapping it so the health module keeps the same `routes → service → repository` shape as every other module.
- Migrations are generated by `drizzle-kit`, committed as SQL, and applied by `npm run db:migrate`.
- The database path comes from `DB_PATH` (default `./data/finance.db`); tests use `:memory:`.

## Consequences

- **Positive:** Schema changes surface as compile errors rather than runtime failures. Migrations are reviewable SQL in version control. A Postgres migration is scoped to two files plus dialect-specific SQL, rather than touching every query. Tests run against a real in-memory SQLite database instead of a mock.
- **Negative:** Dependence on a younger library, so some churn across versions is likely. Two enforced import boundaries add friction and must be maintained by tests rather than by the type system.
- **Neutral:** `PRAGMA journal_mode=WAL` is conditional on a file-backed database, because it has no meaning for `:memory:`. Some SQLite-specific SQL will still exist in committed migrations and would need translating on a Postgres move; the goal is a contained change, not a free one.
- **Operational rule:** an unreachable database is not fatal at boot. The server binds its port and `GET /api/v1/health` reports `db: "unavailable"` with a 503, because a process that refuses to start cannot report why it is unhealthy. Invalid configuration, by contrast, is fatal — see `config.ts`.
